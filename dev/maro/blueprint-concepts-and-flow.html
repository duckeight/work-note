1. 한눈에 보기

Blueprint는 Pit, PiAggregate, PiEntity, PiFeature, PiFacade 같은 VM3 모델보다 먼저 존재하는 재사용 가능한 설계 메타모델이다. 특정 업무의 실제 값은 Blueprint가 아니라 Binding이 가진다.

Blueprint공통 생성 규칙
→
Binding업무 명세·입력·Profile
→
Resolved Model확정 설계 계약
→
MsBindingSetMS 단위 교차 검증
→
VM3Pit / Pi* 생성
단계 간 계약: 다음 Maro 단계는 BlueprintBinding을 직접 소비하지 않는다. Materialize된 기존 VM3를 기존 방식대로 소비한다.
  1. Blueprint는 공통 생성 규칙, Binding은 주문·결제 같은 업무별 설계다.
  2. Profile은 Blueprint 바깥의 독립 StageEntity다.
  3. Binding은 Blueprint와 Profile의 정확한 ID·key·version을 고정한다.
  4. BindingSet 포함 여부와 Materialization 이력은 Binding 수정 가능 여부를 제한하지 않는다.
  5. Aggregate·Move·Feature·Facade Binding은 직접 FK 없이 MsBlueprintBindingSet에 묶인다.
  6. Pit은 개별 Binding ID가 아닌 sourceMsBlueprintBindingSetId만 출처로 보존한다.
  7. 새 PR의 Pit은 직전 최신 PR Pit의 Set 참조를 snapshot하여 동일 Binding ID들을 이어받는다.

2. 도입 목적

기존 방식

사용자가 Entity 값을 직접 입력하고 생성 도중 Aggregate를 지정했다. 결과 모델은 남지만 생성 규칙과 설계 의도는 재사용하기 어렵다.

Blueprint 방식

공통 규칙과 업무 결정을 분리해 보존한다. 같은 Blueprint/Profile로 다른 업무를 일관되게 만들고, 동일 Binding의 변경을 VM3에 다시 반영한다.

공통 생성 규칙 정의
→ 업무 명세와 Profile을 Binding에 결합
→ 최종 Aggregate 설계 resolve
→ VM3 materialize
→ 재사용·추적·변경 동기화

4. 핵심 모델

AggregateBlueprint

입력 스키마, 해석 규칙, 전역 제약, 데이터 이벤트 정책을 가진 공통 기준. ID는 {key}:{version}.

BlueprintProfile

scope, inputDefaults, policies, constraints, tags, active를 가진 독립 StageEntity. ID는 {key}:{version}.

BusinessSpecification

업무 목적·경계·Root·Entity·Field·Operation·Rule·Lifecycle을 보존하는 원본 명세.

AggregateBlueprintBinding

고정된 Blueprint 정체성과 Aggregate 정체성에 업무 명세·입력·Profile·해석 결과를 결합.

ResolvedAggregateModel

Entity, Value, Operation, State, Invariant, Persistence, SDO가 확정된 Materializer 계약.

MsBlueprintBindingSet

타입별 Binding ID 목록과 검증 결과·상태를 가진 마이크로서비스 단위 경계.

AggregateBlueprint의 실행 규칙

AggregateResolutionDefinition
├─ input key mapping
├─ identifier / version rule
├─ transaction / lifecycle defaults
├─ entity generated-field templates
└─ dataObjectTemplates[]: CDO, UDO, DDO, RDO, FDO

Resolver는 blueprintKey를 보고 하드코딩된 구현을 선택하지 않는다. 선택된 Blueprint의 resolutionDefinition을 실행한다.

Binding에서 고정되는 값과 변경되는 값

고정같은 Binding ID에서 변경 가능
blueprintId, blueprintKey, blueprintVersion, aggregateName businessSpecification, inputBindings, profileSelections, resolvedAggregateModel, resolvedDataEventContract, validationResult, status

Aggregate 정체성이나 Blueprint 선택 자체가 달라지면 새 Binding 또는 명시적인 Blueprint migration으로 다룬다.

5. 모델 관계

BindingSet의 목록은 구성원 참조이며 JPA FK 소유 관계가 아니다. 각 Binding의 실행 의존성은 논리 ContractRef로 표현하고 Set에서 교차 검증한다.

6. 전체 생성 흐름

① 카탈로그 준비

실행 가능한 resolutionDefinition을 가진 AggregateBlueprint와 독립 BlueprintProfile을 등록한다.

② 업무 설계

사용자 또는 AI가 목적·경계·Entity·Field·Operation을 입력하고 Blueprint, Profile, Blueprint 입력값을 선택한다. 중단·재개가 필요하면 DesignWork/AuthoringSession 또는 Draft를 사용한다.

③ 결정적 resolve

fixedValue
→ 사용자 BlueprintInputBinding
→ Profile inputDefaults / policies
→ Blueprint defaultValue
→ derivationRule 계산값

이후 ID·Version, Root/Child, Field, SDO, Operation, State, Invariant, Persistence와 Event 계약을 순차 확정한다.

④ BindingSet 구성·교차 검증

AggregateBinding[] + MoveBinding[] + FeatureBinding[] + FacadeBinding[]
+ optional Query / History / Event Binding[]

→ 교차 검증
→ Resolved

⑤ VM3 Materialization

Pit → PiDomain → PiAggregate[]

→ lineage·교차 참조 검증

⑥ 다음 단계

Moti 등은 Binding을 건너뛰고 Materialize된 Pit/Pi*를 기존 방식대로 조회한다.

8. Binding 수정과 Pit 재동기화

Materialization 여부는 Binding의 수정 가능 여부를 결정하지 않는다. Binding은 여러 PR의 Pit VM3 snapshot에 걸쳐 같은 ID로 유지되며 언제든 수정할 수 있다.

카탈로그에서 수정

동일 Binding ID를 다시 resolve하여 갱신한다. 특정 Pit 문맥이 없으므로 기존 Pit VM3 snapshot은 그대로 두고, 필요한 활성 Pit에서 나중에 명시적으로 동기화한다.

Pit 화면에서 수정

동일 Binding ID를 갱신하고 수정 전·후 Resolved 모델 diff를 선택한 활성 Pit에 한 트랜잭션으로 반영한다.

기존 Binding이전 Resolved 보관
→
동일 버전 resolve같은 Binding ID
→
Resolved diffCreate / Update / Remove
→
활성 Pit 동기화한 트랜잭션
반드시 유지갱신 대상
Binding ID, Blueprint ID/key/version, aggregateName, BindingSet ID, Pit source Set ID, 같은 의미 VM3 lineage업무 명세, 입력값, Profile 선택, 해석 결과, 이벤트 계약, 검증 결과와 상태
Materialization 실패 시 확정 Binding은 보존한다. 동일 Binding ID의 같은 해석 결과로 안전하게 재시도할 수 있어야 하며, 일부 생성 상태를 완료로 노출하지 않는다.

9. PR 독립성, Lineage와 출처

새 PR 생성

직전 최신 PR의 Pit/Pi*를 snapshot하고, 새 Pit에 같은 sourceMsBlueprintBindingSetId를 복사하여 Set의 동일 Binding ID들을 이어받는다.

새 PR에서 업무 변경

동일 Binding ID에서 허용 필드를 수정하고 이전/신규 Resolved 모델 diff를 새 PR의 활성 Pit에 반영한다.

여기서 “Binding ID snapshot”은 Binding Entity를 PR마다 복제한다는 뜻이 아니다. Pit이 직전 최신 Pit의 BindingSet 참조를 복사하여 같은 구성원 Binding ID를 계속 사용한다는 의미다.

Lineage 책임

Blueprint, Binding, Resolved 모델에는 최종 lineageId를 두지 않는다. 내부 참조는 aggregateKey, entityKey, fieldKey, objectKey, operationKey를 사용한다.

실제 Drama/Pit/부모 lineage + 이름·경로
→ Geno 등록 흐름의 LineageKeyBuilder
→ 최종 Pi lineageId

출처 역추적

Pit.sourceMsBlueprintBindingSetId
→ MsBlueprintBindingSet.aggregateBindingIds[]
→ AggregateBlueprintBinding.blueprintId
→ AggregateBlueprint

Binding끼리는 직접 FK를 갖지 않는다. 논리 ContractRef를 사용하고 같은 MsBlueprintBindingSet에서 교차 검증한다.

선택 Binding

11. 상태와 검증

Draft→Validated→Resolved또는Failed

VM3 Materialization은 resolve와 validation이 끝난 Binding/BindingSet만 사용한다.

Binding 검증

  • Blueprint/Profile ID·key·version 일치
  • 필수 입력·source·Profile 우선순위
  • Root 1개, Child 소유, 모든 Entity ID
  • Operation·Field·Value·State·Invariant 참조
  • SDO 투영과 Event Policy 호환

Set/Materialization 검증

  • Facade→Feature→Move→Aggregate 참조
  • Move 입출력 타입과 read/write 효과
  • 동일 입력 재실행 멱등성
  • 모든 VM3의 출처 역추적
  • Pit source Set ID 보존과 실패 재시도

14. 금지 사항과 작업 체크리스트

금지 사항

  • Blueprint에 특정 업무 구조 저장
  • Blueprint/Profile/Binding을 PR·Pit이 소유
  • Binding에 prId·pitId·dramaId 추가
  • Blueprint/Resolved 모델에 최종 lineage 저장
  • Blueprint key 기반 Resolver 하드코딩
  • 최신 버전으로 암묵 치환
  • Binding 사이 직접 FK·순환 소유
  • Materializer의 원본 업무 재추론
