# 메인 agent의 순차 기능 개발 지시

## 목적과 범위

사용자와 합의한 설계를 기준으로 designer, implementer, reviewer, tester를 서로 다른 subagent로 순차 실행한다. 이 워크플로를 적용하라는 현재 요청이나 적용 대상 AGENTS.md가 있을 때 사용한다. 단순 설명·조회·오타 수정에는 전체 개발 절차를 강제하지 않는다.

designer는 합의한 설계의 책임자이다. 전체 기능의 새 설계를 독자적으로 작성하는 역할이 아니다. 사용자가 합의하지 않은 업무 결정을 에이전트가 임의 확정하지 않는다.

## 시작 준비

1. `.codex/workflows/common.md`와 적용 대상 지침을 읽는다. 실제 저장소 루트·현재 브랜치·기존 변경을 읽기 전용으로 확인한다. 작업 범위를 분명히 하고 기존 변경을 보존한다.
2. task_id를 정하고 목표, 확정 설계, 설계 원천, 완료 기준, 미정 결정, 허용 변경 범위, 검증 제약을 대화 안의 인계 자료로 정리한다.
3. 이전 대화의 설계에 접근할 수 없으면 사용자가 제공한 요약·명시된 문서를 사용한다. 읽지 못한 대화 내용을 안다고 가정하지 않는다. 핵심 합의가 없으면 사용자와 먼저 정리한다.
4. 역할 파일 네 개가 읽히는지, 요청한 모델과 subagent 실행이 가능한지 확인한다. 기능이 없으면 원인과 가능한 대안을 설명한다. 메인 혼자 역할 이름만 바꾸어 수행한 뒤 별도 agent를 실행했다고 보고하지 않는다.

## 실행 순서

| 단계 | agent | 메인이 전달할 입력 | 다음 단계 진입 조건 |
| --- | --- | --- | --- |
| 1 | designer | 사용자 합의·설계 원천·현재 코드·완료 기준 | 합의 기준과 구현 범위가 명확하며 차단하는 업무 결정이 없음 |
| 2 | implementer | designer의 최신 인계 + 확정 설계 기준 | 필요한 구현 완료, 변경 파일·검증 결과·남은 문제 인계 |
| 3 | reviewer | 최신 설계 기준 + 구현 결과 + 현재 diff | 검토·필요한 범위 내 리팩토링 완료, 미해결 중대 결함 없음 |
| 4 | tester | 최신 설계 기준 + 검토 후 실제 코드 + 완료 기준 | 필요한 테스트가 통과하고 미검증 범위가 명확함 |
| 5 | 메인 | 네 역할의 결과와 현재 작업 트리 | 요구 충족·변경 범위·검증 근거를 직접 확인 |

- 각 역할의 `.codex/agents/<역할>.toml`을 적용해 별도 agent를 생성한다. 사용할 모델과 추론 수준을 역할 파일대로 지정한다. 공통 모델로 임의 통일하거나 동일 agent에게 역할명만 바꿔 연속 수행시키지 않는다.
- 메인 역할 자체의 모델·전역 설정·권한은 변경하지 않는다. agent 수 제한이 있으면 완료된 agent를 종료해 다음 역할의 슬롯을 확보한다. 동시에 네 역할을 실행할 필요는 없다.
- 이전 역할이 결과를 반환하고 작업을 멈춘 것을 확인한 뒤 다음 역할을 시작한다. 메인은 역할이 작업 중인 파일을 동시에 수정하지 않는다. 독립적인 읽기·사용자 대화는 계속할 수 있다.
- 역할은 이전 대화를 자동으로 안다고 가정하지 않는다. 매번 `project_root`, task_id, 최신 design_revision, 목표, 합의·제약, 관련 파일, 이전 역할 인계, 검증 결과를 명시적으로 전달한다. 전체 대화 전문 대신 필요한 결정과 근거를 전달한다.
- 초기 구현부터 결함을 잡는 데 필요한 테스트·빠른 확인을 수행하게 한다. tester는 마지막 변경 상태에서 요구사항 기반 테스트의 충분성과 실행 결과를 책임진다.
- `Ready` 이외의 상태이면 해당 사유를 먼저 처리한다. 사용자가 명시적으로 단계를 생략하도록 요청한 경우에만 그 결정과 미검증 위험을 남기고 순서를 조정한다.

## 설계 합의와 사용자 질문

- designer가 결정·미정·충돌을 구분한 설계 기준을 반환하면 메인은 이를 `D1`로 관리한다. 이 번호는 대화 안의 작업 기준이며 별도의 파일 생성을 요구하지 않는다.
- 현재 합의에 없는 업무 규칙, 공개 API·데이터 의미 변경, 파괴적 데이터 처리, 요청 범위 확대는 메인이 사용자에게 묻는다. 선택지와 영향을 짧게 설명하고 답변이 필요한 변경은 기다린다.
- 확정 설계 안의 내부 구현 방법, 단순 결함 수정, 의미를 보존하는 리팩토링에는 매번 사용자 승인을 요구하지 않는다.
- 사용자가 답변하거나 설계를 수정하면 designer에게 기존 기준과 새 결정을 전달한다. designer가 변경점과 영향 범위를 정리해 `D2` 등 새 기준을 반환하면 영향을 받는 단계부터 다시 수행한다.
- 실행 중 사용자의 질문에는 메인이 답하고, 설계·범위 변경이면 모든 후속 인계에 반영한다. 변경을 무시하고 이전 기준으로 완료하지 않는다.

## 재작업 경로

- 설계 합의 누락·상충: designer가 근거와 질문을 정리하고 메인이 사용자와 해결한다.
- 구현 결함: implementer가 수정하고 reviewer → tester로 다시 진행한다.
- reviewer가 범위 내 리팩토링을 수행했으면 실제 수정 결과에 대해 tester가 검증한다. 동작·계약 변경이 필요하면 먼저 designer에게 영향 판단을 요청한다.
- tester가 테스트·fixture 자체의 오류를 발견하면 그 범위에서 수정하고 다시 확인한다. 제품 코드 수정이 필요하면 implementer로 돌린다. 기존 설계의 변경이 필요하면 designer에게 먼저 보낸다.
- 테스트만 수정한 경우 reviewer가 그 변경을 확인하고 tester가 최종 상태를 검증한다. 해당 확인에서 변경이 없으면 이미 통과한 동일 검증을 이유 없이 반복하지 않는다.
- 환경·도구 문제는 제품 결함과 구분한다. 가능한 대체 검증을 수행하고 실행할 수 없는 필수 검증은 통과로 취급하지 않는다.
- 동일 실패를 근거 없이 반복하거나 합격을 위해 테스트를 약화하지 않는다. 원인을 재분류하고 새로운 확인 방법을 정한다. 사용자 결정·외부 상태가 필요하면 필요한 정보와 남은 작업을 알린다.

## 최종 확인과 보고

메인은 최신 diff를 읽고 기존 사용자 변경을 침범하지 않았는지, 최신 설계와 완료 기준이 충족됐는지 확인한다. agent의 `Ready` 보고만으로 완료를 단정하지 않는다. tester의 검증 이후 제품 코드가 바뀌었다면 영향받는 검토·검증을 다시 수행한다.

최종 응답에는 결과 동작, 중요한 구현·리팩토링, 실제 검증, 미검증·남은 결정을 간결하게 보고한다. 실패·미실행을 성공으로 표현하지 않는다. 요청받지 않은 stage·commit·push·배포나 진행상태 문서 생성을 하지 않는다.
